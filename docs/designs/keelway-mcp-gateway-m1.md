## Problem Statement

Developers connecting autonomous AI agents to MCP servers face a security and operations gap: existing gateways either act as runtime network proxies with weak offline verification (`Agentgateway`), focus on containerized server orchestration (`ToolHive`), or rely on probabilistic prompt-injection detection plugins (`Lasso`). None give developers a testable, explainable, and reproducible **security development lifecycle** for agent tool execution where the security boundary does not depend on whether the underlying LLM recognizes malicious instructions.

Keelway MCP Gateway closes this gap as a local-first, single-binary Rust execution gateway and policy testbench that fits directly into the **Keelway Sovereign Agent Platform** (`kora-sable.vercel.app`, Sorvex Labs).

**Defining principle:** Agents can reason freely, but their ability to act must be explicitly authorized, observable, and controlled.

## What Makes This Cool

One command (`keelway gateway up --config keelway.yaml`) federates three MCP servers behind a single least-privilege endpoint, isolates credentials so agents never touch raw secrets, and streams a live execution console showing every tool discovery, invocation, and policy verdict:

```text
github.read_repository       Coding agent      ALLOWED
github.delete_repository     Coding agent      BLOCKED   (rule: deny-destructive-github)
database.query_readonly      Research agent    ALLOWED
secrets.export               Research agent    BLOCKED   (default-deny: no matching permit)
cloud.deploy                 Enterprise agent  ALLOWED
```

The "whoa" moment: an agent ingests untrusted external content containing a prompt injection that attempts to trigger `github.delete_repository` or `secrets.export`. Keelway blocks the prohibited tool call deterministically at the gateway, records a secret-redacted **SHA-256 hash-chained execution receipt** (matching Keelway's sealed tape on `kora-sable.vercel.app`), and lets legitimate operations continue.

Beyond runtime blocking, Keelway introduces a **security development lifecycle for agent tool execution**:

```bash
keelway init
keelway gateway up --config keelway.yaml
keelway policy test
keelway attack simulate
keelway trace inspect
keelway replay --dry-run
```

Developers can inspect why any tool call was allowed or denied, tighten a policy, and replay recorded execution receipts offline against the updated policy with zero external side effects.

## Constraints

- **Language & Quality Gates (`AGENTS.md`):** Rust-first single binary (`rustfmt`, `cargo clippy -- -D warnings`, `cargo audit`). Zero `.unwrap()` or `.expect()` in production paths. Every non-trivial architectural decision recorded in `docs/adr/` using `docs/adr/000-template.md`.
- **Performance Target:** Under 5 ms p95 gateway processing overhead (excluding upstream MCP server latency). Aspirational target to be measured and verified via benchmark harness before claiming.
- **Security & Isolation (`docs/THREAT_MODEL.md`):**
  - Trust boundary: `Client -> Gateway -> Sandbox/Upstream -> Secret Manager / Storage`.
  - Strict `org_id` + `agent_id` multi-tenant scoping and default-deny authorization.
  - Zero direct exposure of gateway-managed secrets to agents; secrets stripped/redacted from all logs, traces, and tape receipts.
  - `gitleaks` in CI; no committed `.env` files, API keys, or PII/PHI fixtures.
- **Ecosystem Boundary:** Keelway MCP Gateway owns agent connectivity, deterministic execution governance, credential isolation, and hash-chained execution receipts. Information-flow / taint tracking belongs in **IoRa** (clean hook seam reserved, not built in M1).
- **Explicit Milestone 1 Non-Goals:** Kubernetes orchestration, enterprise web dashboards, billing, LLM model routing, full A2A delegation protocol, and IoRa taint tracking are deferred to Milestone 2+.

## Premises

1. **Rust-first Milestone 1:** Replace the 2-line Python healthcheck stub (`src/keelway_mcp_gateway/__init__.py`) as the core runtime and build Milestone 1 directly in Rust rather than prototyping in Python and rewriting later.
2. **Deterministic, explainable default-deny policy engine:** Authorization is strictly default-deny across `org_id`, `agent_id`, server, tool, and arguments, enforcing both `tools/list` filtering and `tools/call` argument/resource validation. Every verdict returns a structured explanation (rule ID, matched/failed predicates, violated argument constraint, policy revision). Threat detection complements, never replaces, deterministic authorization.
3. **Native Keelway hash-chained execution tape + offline replay:** Every mediated MCP call (`ALLOW` and `DENY`) appends a secret-redacted, SHA-256 hash-chained receipt to a local append-only tape (`keelway-tape.jsonl`, aligned with `kora-sable.vercel.app`). `keelway replay --dry-run` re-evaluates recorded receipts against an updated policy file locally with zero upstream calls and outputs an exact allow/deny diff.
4. **Strict 7-capability Milestone 1 boundary + early comparative benchmark:** Milestone 1 ships only: (1) single Rust binary supporting local stdio and remote Streamable HTTP/SSE MCP, (2) 3-server federation behind one endpoint, (3) identity-based default-deny authorization, (4) argument- and resource-level policy enforcement, (5) gateway-managed credential isolation, (6) hash-chained execution traces with structured explanations, and (7) offline `policy test`, `attack simulate`, and `replay --dry-run`, plus a hands-on comparative benchmark against Agentgateway and ToolHive.
5. **Distribution from day one:** Ship `cargo install`, GitHub Releases prebuilt binaries (`darwin-arm64`, `linux-x86_64`) via GitHub Actions CI, and a `curl | sh` `install.sh` matching `kora-sable.vercel.app`, after initializing a dedicated `.git` repository for this workspace.

## Approaches Considered

- **Approach A (Minimal Viable - Single-Crate YAML Policy Compiler + JSONL Tape):** Ruled out because rolling a custom policy language creates long-term precedence/semantics maintenance debt and requires refactoring into crates later to integrate with the broader Keelway platform.
- **Approach C (Lateral - Security-SDK-First Engine + Built-In Attack Lab + Thin Gateway Adapter):** Ruled out as the primary architecture because focusing on synthetic mocks first risks under-investing in real stdio and Streamable HTTP MCP transport edge cases; however, its zero-setup 3-server local demo fixture is folded into Approach B under `examples/`.
- **Approach B (Selected - Multi-Crate Rust Workspace + Native Cedar Policy Engine + Keelway Tape):** Modular Cargo workspace with pure-Rust `cedar-policy`, typed argument validators, `arc-swap` hot reload, and native Keelway SHA-256 hash-chained receipts.

### Key Architectural Decisions

1. **Client Authentication & Fail-Closed Principal Binding (`keelway-mcp` + `keelway-core`):**
   - **Streamable HTTP/SSE:** Clients authenticate via `Authorization: Bearer <token>` (configured in `keelway.yaml` using `secret://...` references or HMAC/JWT verification) mapped deterministically to a `Principal { org_id, agent_id, roles }`. Missing, malformed, or unknown credentials fail closed with HTTP `401 Unauthorized` before `tools/list` or `tools/call` executes and append a `DENY` receipt (`reason: unauthenticated`).
   - **Local stdio:** Local sessions bind an explicit principal at launch via `--principal <org_id>/<agent_id>` (or a named profile in `keelway.yaml`). Starting stdio mode without a valid principal fails closed at startup with a non-zero exit code.
2. **Canonical Federated Tool Namespacing (`keelway-mcp`):**
   - On the MCP wire protocol, federated tool names use `<server_alias>__<sanitized_tool_name>`, where any character in `upstream_tool_name` outside `[a-zA-Z0-9_-]` (such as `.` or `/`) is deterministically replaced with `_` so every wire `federated_name` strictly satisfies `[a-zA-Z0-9_-]` for strict MCP clients. The terminal console may render a readable display alias (e.g., `github.read_repository`).
   - Startup validation enforces `server_alias` matches `^[a-z0-9-]+$` (never containing `__`), builds an unambiguous bidirectional routing table `federated_name <-> (server_alias, exact_upstream_tool_name)`, and fails closed if any two upstream tools collide after sanitization or if an alias is invalid. `tools/call` reverses `federated_name` to the exact upstream tool name via this table, and Cedar always evaluates against `Tool::"<server_alias>/<exact_upstream_tool_name>"`.
3. **Pure-Rust Cedar + Deterministic 2-Stage Argument Validation (`keelway-policy`):**
   - Milestone 1 ships exactly five typed argument validators: `path_within`, `glob`, `regex`, `sql_readonly`, and `repo_allowlist`.
   - **Stage 1 (Typed Validators -> Cedar Context):** Before Cedar runs, `keelway-policy` evaluates validators bound in `keelway.yaml` to `(server_alias, upstream_tool_name, arg_name)` against the request arguments and injects their boolean results into Cedar `Context` (e.g., `context.arg_checks.path_within_workspace == true`). `path_within` performs pure lexical normalization (resolving `.` and `..` and normalizing separators without querying the host filesystem) so offline `replay --dry-run` is 100% deterministic; host symlink traversal is an OS-sandboxing concern deferred to Milestone 2+.
   - **Stage 2 (Cedar Evaluation):** `cedar-policy` (pure Rust, zero FFI, sub-millisecond evaluation) evaluates `permit` and `forbid` policies against `(principal, action, resource, context)` using Cedar's formally verified default-deny and forbid-overrides-permit semantics. Because validators feed into Cedar `when { ... }` / `unless { ... }` predicates, a failed validator can never override a `forbid` rule, and `Explanation` reports the exact Cedar `rule_id`, matched/failed predicates, and failing `validator_id` + `arg_name`.
   - **Hot Reload Without Downtime:** Compiled policy snapshots live behind `arc-swap::ArcSwap`. File changes or `SIGHUP` validate and atomically swap the snapshot; invalid edits are rejected while keeping the last known-good snapshot live.
4. **Single-Writer Hash-Chained Tape, Fail-Closed Persistence & Offline Replay (`keelway-tape`):**
   - A dedicated single-writer task consumes receipts over a bounded `tokio::sync::mpsc` channel with oneshot acks, guaranteeing strictly monotonic `seq` and linear SHA-256 `prev_hash -> entry_hash` chaining under concurrent HTTP/SSE traffic, flushing and calling `sync_data()` before acknowledging.
   - **Fail-closed persistence & startup integrity:** An `ALLOW` decision receipt must be persisted before dispatching the upstream MCP call; if tape persistence fails, the gateway fails closed (`-32001 TapePersistenceError`) and does not invoke the upstream tool. On startup, if an existing `keelway-tape.jsonl` fails SHA-256 chain verification, the gateway refuses to start until rotated or pointed at a clean tape path.
   - **Upstream timeouts & stdio crashes:** Every upstream call enforces a configurable `timeout_ms` (default 30s). Timeouts or stdio child-process crashes return structured JSON-RPC errors (`-32002 UpstreamTimeout` / `-32003 UpstreamUnavailable`), append a paired outcome receipt (`outcome: timeout | crashed`), and trigger bounded exponential-backoff restart for stdio children.
   - **Live/Replay Parity & Redacted Fields:** Every `Receipt` stores `seq`, `prev_hash`, `entry_hash`, `timestamp`, `org_id`, `agent_id`, `server`, `tool`, `redacted_args`, `redacted_fields` (JSON Pointer paths of any scrubbed argument fields), `decision`, `explanation`, `policy_digest`, and an extensible `state` (`SEALED` / `BLOCKED` / future `AWAITING` for P-10 human gates) plus an optional provenance slot for IoRa. Because gateway-managed secrets are injected downstream, `redacted_fields` is empty on normal calls and `keelway replay --dry-run` invokes the exact same `evaluate(policy_snapshot, principal, tool_call)` function with 100% parity. If an agent unexpectedly passes a secret inside tool arguments and an evaluated constraint touches a path in `redacted_fields`, replay explicitly marks that verdict `INDETERMINATE (redacted_field_touched)` instead of emitting a false `ALLOW` or `DENY`.
5. **Credential Isolation & Streaming Secret Scrubbing (`keelway-secrets`):**
   - Upstream configs reference secrets via `secret://env/GITHUB_TOKEN` or `secret://file/...` (with a trait seam for GCP Secret Manager + OIDC). Secrets resolve strictly inside the gateway process and are injected only into upstream HTTP headers or stdio child env vars.
   - Resolved secrets (minimum length >= 8 bytes) and their common encodings (raw, JSON-escaped, URL-encoded, Base64) are compiled into an in-memory Aho-Corasick scrubber. Streaming SSE responses use a sliding-window buffer of `max_secret_len - 1` bytes across chunk boundaries to catch straddling secrets, and stdio child `stderr` is captured and scrubbed alongside `stdout` before logging or forwarding.
   - **Threat-model boundary:** Gateway scrubbing prevents accidental or naive leakage of gateway-managed secrets (raw, JSON-escaped, URL-encoded, Base64) across tool outputs, SSE streams, stderr, console, and tape, but cannot prevent arbitrary custom obfuscation/steganography by a malicious upstream server (which requires OS/egress sandboxing in Milestone 2+).

## Success Criteria

- `keelway gateway up --config keelway.yaml` federates 3 MCP servers behind one endpoint and serves filtered `tools/list` per authenticated agent identity.
- A live prompt-injection test scenario attempting `github.delete_repository` and `secrets.export` is deterministically blocked at the gateway while legitimate `github.read_repository` and `database.query_readonly` calls succeed.
- Zero gateway-managed secret values (raw, JSON-escaped, URL-encoded, or Base64, >= 8 bytes) appear in agent-visible responses (including chunk-straddling SSE streams), stdio stderr, terminal output, or `keelway-tape.jsonl`.
- `keelway trace inspect` verifies the SHA-256 hash chain (`chain verified`) and displays structured ALLOW/DENY explanations for every call.
- `keelway policy test`, `keelway attack simulate`, and `keelway replay --dry-run` all run offline with zero upstream MCP calls and return deterministic exit codes for CI.
- `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, `cargo audit`, and `gitleaks` all pass in GitHub Actions CI.
- Measured p95 gateway overhead benchmarked and documented honestly (target < 5 ms p95 excluding upstream calls).
